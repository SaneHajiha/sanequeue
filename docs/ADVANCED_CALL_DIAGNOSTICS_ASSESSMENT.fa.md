# ارزیابی فنی Advanced Call Diagnostics

تاریخ: ۲۰۲۶/۱۰/۲۸ · وضعیت: **پیشنهاد برای تأیید؛ ماژول پیاده‌سازی نشده است.**

این گزارش پاسخ «First Task» است. پس از دستور گزارش‌محور، هیچ کد عملیاتی، Dialplan، تنظیم CEL/CDR، Debug، سرویس یا قابلیت PBX تغییر داده نشد. بررسی سرور فقط خواندنی بود و تماس جدیدی برقرار نشد. تغییرات قبلی فهرست ماژول‌ها/CSV/کال‌بک، کار مرحلهٔ قبل‌اند؛ وجود آن‌ها به معنی شروع Diagnostics نیست.

## نتیجهٔ اصلی

SaneQueue زیرساخت قابل استفاده‌ای دارد، اما هنوز ابزار تشخیص تاریخی صدای یک‌طرفه یا علت قطعی قطع تماس نیست. سه پیش‌نیاز اصلی عبارت‌اند از: **تضمین تازگی منبع تاریخی، اتصال معتبر legهای تماس و افزودن شواهد جهت‌دار سیگنالینگ/رسانه**. برای تحلیل اولیه نیازی به AI یا GPU نداریم. تشخیص باید ابتدا rule-based، قابل بازپخش و مبتنی بر شاهد باشد.

دریافت BYE از تلفن، علت فنی و قصد انسان سه موضوع متفاوت‌اند. همچنین «پایان بخش صف توسط کارشناس» لزوماً پایان کل مکالمه پس از انتقال نیست.

## ۱. دامنهٔ بررسی و وضعیت واقعی سرور

ساختار ۱۰۲ فایل Python در sanequeue، ۳۵ فایل در qpanel و ۶ اسکریپت بررسی و با AST خوانده شد؛ خطای parse مشاهده نشد. مسیرهای تولید/مصرف مرتبط با collector، correlation، journey، SQL importer، ذخیره، API، مجوز و کیفیت به‌صورت تفصیلی خوانده شدند و دو بررسی مستقل کدی انجام شد. **این بررسی، ممیزی تک‌تک خطوط کل مخزن یا گواه نبود باگ نیست.**

مبنای کد محلی، working tree دارای تغییرات انباشته است؛ HEAD محلی با شاخهٔ منتشرشده یکی نیست. بنابراین نتیجه به فایل‌های بررسی‌شده مربوط است، نه ادعای یک release نهایی منتشرشده.

بررسی واقعی سرور آزمایشی:

| مورد | مشاهده | معنی و محدودیت |
|---|---|---|
| نسخه | Asterisk 20.12.0 | شناسایی واقعی همین میزبان؛ پشتیبانی همهٔ نسخه‌های 16/18/20 هنوز آزموده نشده |
| CEL | Logging Enabled؛ Tracking Event: ALL و رخدادهای Answer/Hangup/Bridge/Transfer/Local | ثبت CEL فعال است؛ انتقال همهٔ فیلدها به SaneQueue باید جدا بررسی شود |
| مصرف‌کننده CEL | Custom CSV و ODBC در `cel show status` | برای تاریخچه منابع بالقوه موجودند |
| CEL Manager | ماژول بارگذاری شده، ولی subscriber مربوط در خروجی status دیده نشد؛ فایل استاندارد cel_manager.conf موجود نبود | دریافت CEL از AMI تأیید نشد؛ بارگذاری ماژول به‌تنهایی کافی نیست؛ include یا تنظیم جایگزین نیز ممکن است وجود داشته باشد |
| CDR | Logging Enabled؛ Adaptive ODBC، custom و CSV؛ cdr_manager suspended | CDR محلی فعال است؛ رویداد CDR از Manager را فعال فرض نمی‌کنیم |

| تازگی آرشیو | آخرین CEL: 2026-10-26 20:45:56 تهران؛ آخرین CDR: 20:45:51 همان روز | برای رخداد تازهٔ امروز کافی نیست؛ سلامت منبع باید جدا از سلامت projection سنجیده شود |
| سرویس‌ها | collector و preview فعال؛ reporting importer غیرفعال | ابتدا باید علت توقف/روش فعلی ingest بررسی و پس از تأیید اصلاح شود؛ در این مرحله سرویسی فعال نشد |
| مسیر استاندارد آرشیو اصلی | history.sqlite3 در مسیر استاندارد state اصلی مشاهده نشد | اثبات نبود هر آرشیو دیگری در تنظیم سفارشی نیست؛ دادهٔ مشاهده‌شده مربوط به preview است |
| رسانه | res_rtp_asterisk بارگذاری شده | اثبات دریافت RTCP یا وجود رسانهٔ دوطرفه نیست |
| سه داخلی آزمایشی PJSIP | direct_media=false، rtp_symmetric=true، force_rport=true، rewrite_contact=true؛ rtp_timeout و rtp_timeout_hold صفر | فقط تنظیم همین سه داخلی است؛ تنظیم ترانک یا مسیر واقعی هر تماس را اثبات نمی‌کند |
| تماس هنگام بررسی | صفر تماس فعال | هیچ اندازه‌گیری کیفیت صوت یا سربار زیر بار انجام نشد |

دادهٔ مشتری، شماره‌ها، رمزها، فایل صوتی و محتویات خام SIP در این گزارش درج نشده‌اند. این میزبان، سرور مشکل‌دار شرکت را نمایندگی نمی‌کند تا زمانی که همان منابع در مقصد نیز بررسی شوند.

| آرشیو append-only و cursor | `reporting/store.py`، `sources.py` و `sql_source.py` | ingest در worker است؛ HTTP نباید به AMI/SQL عملیاتی مراجعه کند |
| leg و edge دارای provenance | `reporting/correlate.py` | کلید leg از PBX و Uniqueid؛ Linkedid به‌تنهایی مجوز یا رابطه قطعی نیست |

| RTCP زنده | `state.py:218`؛ `qpanel/operations.py:603` | آخرین نمونه، نه سری زمانی تاریخی و نه اثبات یک‌طرفه بودن |
| محدودهٔ صف/کارشناس، شماره‌پوشانی و صوت | `api/reports.py`، `recording_scope.py` و `privacy.py` | graph مسیر تماس به‌خودی‌خود مجوز صوت یا مشاهدهٔ طرف ثالث نمی‌دهد |
| خروجی، نمودار، audit و گزارش‌ها | ماژول‌های reporting/API | قابل استفاده مجدد با قراردادهای جدید؛ خروجی Diagnostics هنوز وجود ندارد |

دو نام فعلی نباید اشتباه تفسیر شوند: `pbx/incidents.py` برای **پیام صوتی اطلاع‌رسانی ورودی** است؛ کارتابل incident فنی نیست. `reporting/quality.py` فرم **ارزیابی انسانی مکالمه** است؛ اندازه‌گیری RTP نیست.

### شکاف‌های مشخص Call Journey

1. ورودی SQL CEL، `userdeftype` را انتخاب نمی‌کند، ولی نمایش USER_DEFINED مربوط به IVR به آن نیاز دارد. موفقیت fixture JSON، صحت همین مسیر SQL را ثابت نمی‌کند.
2. نمایش LOCAL_OPTIMIZE_END با تولید edge متناظر در projector یکسان نیست؛ پوشش BEGIN/END باید هماهنگ شود.
3. قطع نهایی به علت صریح `hangupsource_uniqueid` و رابطهٔ دو leg مستقیم نیاز دارد. تبدیل عمومی `hangupsource` خام به UID و تولید عمومی `direct_peer` در مسیر فعلی پیدا نشد؛ بخش‌هایی از آزمون‌ها از شاهد مصنوعی استفاده می‌کنند.
4. تماس داخلی‌به‌داخلی خارج از صف، ورودی طبیعی همان endpoint گزارشِ visit صف نیست؛ لازم است مدل conversation/leg عمومی اضافه شود.
5. انتقال چندمرحله‌ای/کنفرانس عمداً قطع‌کنندهٔ نهایی را نامشخص می‌گذارد. زمان مشورت در projection فعلی بدون شاهد اضافی NULL است.
6. Hold/Unhold زنده وجود دارد، ولی پوشش تاریخی آن برای این تشخیص‌ها کامل نیست. موتور journey زنده best-effort است و نباید با graph تاریخی دارای مجوز و شواهد یکسان فرض شود.

## ۳. اکنون چه داده‌ای داریم و چه چیزی کم است؟

| داده | وضعیت فعلی | نیاز توسعه/فعال‌سازی پس از تأیید |
|---|---|---|
| Uniqueid، Channel، Linkedid | موجود، وابسته به منبع | epoch/generation منبع، Rename/Local/transfer و ambiguity صریح |
| ورود صف، پاسخ، پایان segment | موجود | حفظ جدایی segment از کل conversation |
| Bridge و Transfer | CEL/AMI موجود به‌صورت مشروط | مسیر عمومی تماس داخلی، شروع/پایان bridge و transfer با provenance کامل |
| Trunk/Endpoint/Agent | بخشی از inventory و CDR/صف | نگاشت معتبر leg به endpoint/trunk در زمان رخداد؛ از طول شماره یا پیشوند channel حدس نزنیم |
| Hangup cause | در منبع CEL ممکن است موجود باشد | فیلد استانداردشده، source خام محدودشده، علت گمشده/متناقض و نقش هر leg |
| SIP Call-ID و dialog | مسیر canonical اختصاصی پیدا نشد | Call-ID + tags + leg mapping؛ Call-ID با Uniqueid یا Linkedid برابر نیست |
| BYE/CANCEL/Reason/status/timeout | مسیر آرشیوی ساختاریافته پیدا نشد | آداپتور سیگنالینگ اختیاری، جهت پیام و سمت مشاهده؛ CANCEL معمولاً به تلاش پاسخ‌داده‌نشده مربوط است |
| Codec/clock-rate/SDP | تاریخچهٔ مرتبط با تماس موجود نیست | snapshot مجاز در مذاکره/تغییر رسانه، بدون secrets و SDP خام عمومی |
| RTCP RTT/loss/jitter | آخرین نمونهٔ زندهٔ کانال شناخته‌شده | ذخیرهٔ خلاصه تاریخی، SSRC/report block، جهت و freshness؛ parser چند report block |
| packet counters/مسیر RTP | در مدل فعلی نگهداری کامل ندارد | منبع واقعی و مجاز برای RX/TX و آدرس‌های مذاکره‌شده/مشاهده‌شده |
| direct_media | inventory/diagnosis فعلی ندارد | تنظیم endpoint و مسیر واقعاً مذاکره‌شده برای هر تماس، جدا از هم |
| گزارش مشکل توسط کاربر | کارتابل فنی اختصاصی ندارد | ثبت مستقل، شناسه پیگیری و اتصال دارای شاهد به تماس |

مدل فعلی RTCP، RTT را به ms و fraction lost را به درصد تبدیل می‌کند، اما jitter را به صورت timestamp ticks نگه می‌دارد؛ تبدیل به ms بدون clock-rate معتبر خطاست. فقط report شماره صفر فعلاً مصرف می‌شود و با پایان کانال نمونه از state حذف می‌شود. SIP Qualify RTT نیز جای RTT رسانه نیست. ساختار و واحدها در [مستند رسمی RTCPReceived](https://docs.asterisk.org/Asterisk_20_Documentation/API_Documentation/AMI_Events/RTCPReceived/) مشخص‌اند.

## ۴. تشخیص دو مشکل شرکت

### صدای یک‌طرفه

مسیر بررسی باید برای **هر leg و جهت** باشد: تولید صدا در تلفن کارمند → دریافت رسانه در PBX، اگر در مسیر است → ارسال به leg مشتری → دریافت/پخش در مقصد. در جهت سالم نیز همین نقاط با بازهٔ زمانی یکسان مقایسه می‌شوند.

لازم است SDP اولیه و re-INVITE/UPDATE، آدرس/پورت مذاکره‌شده در مقابل مشاهده‌شده، codec/clock، RX/TX و RTCP دارای پوشش مقایسه شوند. شکست محدود به endpoint، ترانک، نسخه firmware، کدک یا مسیر شبکه با **تعداد رخداد و تعداد کل تماس‌های دارای پوشش همان گروه** گزارش شود؛ صرفاً تعداد شکایت‌ها نرخ خرابی نیست.

نبود بسته در نقطهٔ مشاهده می‌تواند قرینهٔ مسیر رسانه باشد، اما فقط وقتی انتظار عبور رسانه، زمان پاسخ، hold، DTX/silence suppression، ICE/SRTP و Direct Media معلوم باشد. وجود packet نیز وجود صدای قابل شنیدن، میکروفون سالم یا صدای انسان را ثابت نمی‌کند. صدای mixed تک‌کاناله برای تشخیص مستقل دو طرف کافی نیست. تحلیل سطح انرژی صوت دوکاناله، اگر بعداً مجاز شود، قابلیت جدا و اختیاری خواهد بود؛ AI شرط شروع این ماژول نیست.

در Direct Media ممکن است رسانه از PBX عبور نکند؛ نبود RTP روی PBX نباید «صدای یک‌طرفه» ثبت شود. مشاهدهٔ endpoint/SBC/SPAN یا شاهد نقطهٔ دیگر لازم می‌شود. حتی direct_media=false در تنظیم، به‌تنهایی تاریخچهٔ مذاکرهٔ یک تماس خاص نیست. [مرجع رسمی NAT و Direct Media](https://docs.asterisk.org/Configuration/Channel-Drivers/SIP/Configuring-res_pjsip/Configuring-res_pjsip-to-work-through-NAT/)

### قطع غیرمنتظره پس از پاسخ/انتقال

Timeline باید تلاش تماس، پاسخ هر leg، bridge membership، Hold، Blind/Attended Transfer، leg مقصد و پایان‌ها را جدا نمایش دهد. «اولین HANGUP دیده‌شده» فقط ترتیب مشاهده است؛ تأخیر منبع، زمان سیستم، انتقال موفق یا Local optimization می‌تواند ترتیب گمراه‌کننده ایجاد کند.

چهار لایهٔ نتیجه جدا باشند:

| لایه | نمونهٔ صحیح نمایش |
|---|---|
| Observed signaling | BYE از dialog مرتبط با endpoint دریافت شد؛ زمان و محل مشاهده مشخص |
| Asterisk cause | cause ثبت‌شدهٔ PBX؛ بدون نسبت‌دادن قصد انسان |
| Inferred technical cause | قطع پس از RTP inactivity با شاهد ناقص؛ فرضیه و شاهد مخالف ذکر شود |
| Confirmed root cause | علت محدود و مشخص با شاهد کافی/آزمون کنترل‌شده و ثبت تأیید بازبین |

BYE از یک تلفن، بین زدن دکمهٔ قطع، رفتار softphone/firmware یا تصمیم خود دستگاه تمایز قطعی نمی‌دهد. Cause 16، پاسخ SIP 487 یا قطع leg انتقال‌دهنده به‌تنهایی دلیل خرابی یا قطع عمدی نیست. ارتباط قطع با Dialplan، محدودیت مدت یا timeout باید با اجرای مسیر مربوط و زمان‌بندی معتبر اثبات شود. تغییر هم‌زمان چند تنظیم و بهترشدن وضعیت نیز علت واحد را ثابت نمی‌کند. [مستند رویدادهای CEL و سناریوهای انتقال](https://docs.asterisk.org/Configuration/Reporting/Channel-Event-Logging-CEL/CEL-Specification/)

## ۵. معماری افزایشی پیشنهادی

مسیر پایه: collector موجود / واردکنندهٔ CDR-CEL → آرشیو و feed محدود → worker تشخیصی مستقل → read model تشخیص → API دارای مجوز → Dashboard/Timeline/Reports.

- Call Journey موجود حفظ می‌شود؛ graph عمومی conversation/leg به آن افزوده می‌شود. رابطهٔ مشاهده‌شده، استنباطی، مبهم و ناقص فیلدهای مجزا دارند. Linkedid، شماره یا نزدیکی زمان به‌تنهایی سبب ادغام یا افزایش مجوز نمی‌شوند.
- از همان اتصال collector استفاده شود؛ برای هر refresh یا هر کاربر AMI connection/query تازه نسازیم. worker تشخیصی نباید دریافت collector را بلوکه کند.
- ابتدا ingest تاریخی جاری، source cursor و lag اصلاح/تأیید شوند؛ تازگی projection به معنی تازگی CEL نیست. دریافت CEL از Manager یا SQL/CSV یک انتخاب مهندسی وابسته به نسخه/پیکربندی است، نه فرض نصب.
- برای PJSIP، مستند رسمی قابلیت خواندن SIP Call-ID و اطلاعات RTP/RTCP از CHANNEL را شرح می‌دهد؛ مسیر عملی دریافت و scope هر leg باید بعد از تأیید و روی نسخهٔ هدف آزموده شود. chan_sip آداپتور جدا لازم دارد. [مرجع CHANNEL](https://docs.asterisk.org/Asterisk_20_Documentation/API_Documentation/Dialplan_Functions/CHANNEL/)
- collector سیگنالینگ پیشرفته اختیاری است. Full SIP/RTP debug دائمی پیش‌فرض نیست. metadata حداقلی قبل از ذخیره redaction شود؛ raw capture به مجوز، دامنه، سقف زمان/حجم، توقف اضطراری و audit جدا نیاز دارد.
- TLS/SRTP و Direct Media محدودیت مشاهده دارند؛ برای رفع آن‌ها کلیدها یا رمزهای رسانه صادر نمی‌کنیم. غیرفعال‌سازی رمزنگاری/NAT یا تغییر Direct Media راه‌حل خودکار این ماژول نیست.
- قطع شدن ماژول تشخیصی، پذیرش/جمع‌آوری اختیاری را متوقف می‌کند؛ به مسیر تماس، SIP routing یا خود Asterisk فرمان قطع نمی‌دهد.

| incident_action | گزارش‌کننده، تغییر وضعیت، بازبین، یادداشت و نتیجهٔ بررسی به‌صورت append-only |
| diagnostic_checkpoint / source_health | cursor پردازش، lag، بازه‌های گم‌شده و علت محدودیت جمع‌آوری |

SQLite جدا برای read model تشخیص، با WAL و یک writer محدود، وابستگی نوشتن را از PBX و آرشیو اصلی جدا می‌کند. cursor و projection تشخیصی در یک transaction همان دیتابیس commit شوند؛ replay با کلید یکتای source generation/key/rule idempotent باشد. backup/restore باید UUID/generation آرشیو و مراجع شواهد را هماهنگ حفظ کند. hash محتوا، احراز اصالت منبع نیست.

ایندکس‌های ابتدایی: `(pbx,last_seen,id)`، `(pbx,category,last_seen,id)`، `(incident_id,observed_at,id)`، `(pbx,leg_id,observed_at,id)` و `(queue,incident_id)`؛ انتخاب نهایی با EXPLAIN و حجم واقعی تأیید شود. join غیرمحدود روی PBX یا تراکنش طولانی برای Excel مجاز نباشد.

### نگهداری و امنیت

مطابق سیاست پروژه، incident، خلاصه، نتیجه و audit حذف خودکار ندارند. شواهد خام آرشیو دوباره کپی نمی‌شوند. بافر گذرای RAM با تاریخچهٔ ثبت‌شده متفاوت است؛ انقضای آن پوشش را محدود می‌کند و باید معلوم باشد. raw trace اختیاری تا زمان انتخاب صریح سیاست نگهداری فعال نمی‌شود. کمبود دیسک باید جمع‌آوری اختیاری را متوقف و gap ثبت کند، نه تاریخچه یا صوت را خودکار پاک کند.

مجوزهای پیشنهادی مستقل: `diagnostics.view`، `report`، `investigate`، `capture.request`، `capture.approve`، `evidence.export`، `network_details` و `confirm_root_cause`. کارشناس فقط تماس‌های متعلق/مجاز خود را می‌بیند؛ رخداد چندصفی مجوز جاری همهٔ صف‌های مرتبط را می‌خواهد. تماس داخلی بدون صف نیازمند policy صریح داخلی/تماس است؛ grant یک صف مجوز کل PBX نیست. لیست، count، نمودار، export و فایل شواهد همگی باید همین مرز را رعایت کنند.

Authorization، password، ICE password، کلید SRTP، مسیر فایل و payload صوت وارد API، اعلان یا بستهٔ بازبینی عمومی نشوند. IP شبکه و SIP Call-ID هم اطلاعات فنی دارای مجوزند. متن کاربر plain text است؛ upload، URL یا command آزاد قابل اجرا نیست. مشاهدهٔ graph، مجوز شنیدن ضبط ایجاد نمی‌کند.

## ۶. سربار و سقف‌های پیشنهادی

**سربار واقعی Diagnostics هنوز اندازه‌گیری نشده است، زیرا ماژول ساخته/فعال نشده و هنگام بررسی تماس فعالی وجود نداشت. عدد صفر یا تضمین بدون اختلال قابل ارائه نیست.** خواندن metadata موجود معمولاً به مسیر رسانه دست نمی‌زند؛ تولید event اضافی، capture، log I/O و ازدحام worker هرکدام باید اندازه‌گیری شوند.

پیشنهاد شروع پایلوت، قابل بازنگری پس از سنجش:

| بخش | بودجهٔ پیشنهادی |
|---|---|
| worker | تک worker، سقف 0.1 هسته CPU، MemoryMax=128MiB، Nice=10 و IO priority پایین |
| ورودی | صف محدود و بدون backpressure به collector؛ ظرفیت بر اساس نرخ event و آزمون ۵۰/۱۰۰ تماس انتخاب شود؛ lag/gap قابل مشاهده |
| UI | صفحهٔ ۱۰۰ ردیفی؛ query هدف حداکثر ۱ ثانیه؛ جزئیات محدود و خروجی بزرگ پس‌زمینه |
| حالت عادی | خلاصهٔ پایان leg و شواهد رخداد؛ بدون ذخیرهٔ مداوم RTP payload یا تمام SIP |
| capture موردی | پیش‌فرض خاموش؛ یک capture هم‌زمان، حداکثر ۱۲۰ ثانیه یا ۵۰MiB، هرکدام زودتر؛ توقف در فشار منابع |

این اعداد **تنظیم پیشنهادی‌اند، نه ظرفیت اثبات‌شده**. سقف worker، هزینهٔ ساخت event در Asterisk یا packet processing کرنل را محدود نمی‌کند. نرخ پردازش ثابتِ کمتر از نرخ ورود باعث رشد lag می‌شود و معیار پذیرش نیست.

مثال ظرفیت ذخیره: ۱۰۰ تماس × دو leg × دو جهت ÷ ۱۰ ثانیه = ۴۰ نمونه در ثانیه. حتی با فرض فقط ۲۵۶ بایت برای هر نمونه، حدود ۰٫۹GB دادهٔ خام در روز تولید می‌شود؛ ایندکس/WAL نیز هزینه دارند. بنابراین ذخیرهٔ سری زمانی همهٔ تماس‌ها بدون خلاصه‌سازی، سبک تلقی نمی‌شود. این محاسبهٔ فرضی، اندازه‌گیری فایل واقعی نیست.

## ۷. آزمون‌های لازم

۱. **مصنوعی و بازپخش:** duplicate، out-of-order، clock skew، rotation، reconnect، restore generation و قطع منبع؛ هیچ‌کدام نباید تشخیص قطعی بسازند یا رخداد را دو بار بشمارند.

۲. **پایان تماس:** تماس مستقیم داخلی و صف، قطع از هر سمت، Blind/Attended Transfer، کنفرانس، Local با/بدون optimization، bridge exit طبیعی، timeout واقعی و Dialplan duration limit؛ «پایان leg انتقال‌دهنده» با «پایان مشتری» تفکیک شود. BYE از تلفن همیشه بدون ادعای قصد انسان گزارش شود.

۳. **رسانه در آزمایشگاه:** صدای مرجع دوطرفه، قطع انتخابی یک جهت RTP، mic mute/فقدان میکروفون، hold/resume و sendonly/inactive، DTX، تغییر SDP، NAT، Direct Media، codec/clock-rate مختلف، SRTP و RTCP گمشده/چند report block. دادهٔ ناقص باید Unavailable بسازد؛ MOS یا jitter ms حدسی ممنوع است.

۴. **مجوز:** تماس چندصفی و داخلی خارج صف، مالکیت ضبط، لغو دسترسی وسط export/capture، عدم نشت شماره/طرف تماس/IP/تعداد رخداد و تزریق در متن/فیلتر.

۵. **کارایی:** baseline بدون Diagnostics، سپس metadata و در نهایت capture محدود روی همان سناریوهای ۵۰ و ۱۰۰ تماس آزمایشی. CPU/RSS/I/O، دیسک/WAL، lag رویداد، زمان برقراری، پاسخ/قطع و معیارهای رسانه مقایسه شوند. مصرف مدل ASR جدا سنجیده شود. کیفیت تماس افت کند یا منبع از سقف بگذرد، جمع‌آوری اختیاری متوقف شود. این آزمون هنوز اجرا نشده است.

۶. **نسخه/فناوری:** Asterisk 16/18/20، SIP و PJSIP، Issabel 4/5 فقط روی محیط مربوط تأیید شوند؛ نبود قابلیت، Unavailable با علت بدهد. موفقیت یک نسخه جای ماتریس سازگاری نیست.

۷. **پذیرش گزارش/UI:** count و drill-down یک بازه/فیلتر برابر باشند؛ تشخیص‌های احتمالی از root cause تأییدشده جدا؛ فارسی/انگلیسی، شمسی/میلادی، RTL/LTR، روشن/تیره، موبایل، کیبورد و تمام حالت‌های نبود داده/خطا بررسی شوند.

## ۸. طرح UI/UX و نقشهٔ اجرا

در گروه «سلامت و عیب‌یابی تماس»: داشبورد رخدادها، گزارش مشکل، جزئیات تماس/Timeline، رسانه، گزارش تاریخی و تنظیم جمع‌آوری. از تماس جاری/گزارش مکالمه نیز مسیر «گزارش مشکل» با اطلاعات ازپیش‌پرشده و تأیید کاربر ارائه شود.

در هر جزئیات چهار بخش مستقل نمایش یابد: **مشاهدات، علت ثبت‌شده PBX، فرضیه فنی، علت تأییدشده**. کارت کیفیت منبع، زمان آخرین شاهد، پوشش و محدودیت Direct Media کنار نتیجه باشد. Confidence اولیه کیفی باشد؛ درصد دقت بدون کالیبراسیون نمایش ندهیم. نمودار تکرار مشکل مخرج و میزان پوشش خود را نشان دهد.

| مرحله | خروجی | دروازهٔ پذیرش |
|---|---|---|
| ۰. ممیزی منبع | تشخیص توقف ingest، داده/مجوزهای موجود، schema فیلدها و capability matrix | شاهد CEL/CDR تازه از تماس آزمایشی و lag مشخص |
| ۱. شواهد و graph | normalization علت قطع، UID/Channel/Dialog mapping، تماس داخلی و انتقال | آزمون بازپخش و نبود ادغام/افشای بی‌دلیل |
| ۲. تشخیص پایه و incident | ثبت مشکل، short-after-answer/transfer و علت‌های مشروط | fixture مثبت/منفی و unknown درست؛ بدون debug جدید |
| ۳. UI و گزارش | طرح Figma، جریان کار Product Design، کامپوننت/Storybook، سپس پیاده‌سازی پس از تصویب | Playwright، مجوز، دسترس‌پذیری و تطبیق نمودار/ریز |
| ۴. رسانهٔ اختیاری | خلاصه RTCP/codec/SDP و capture محدودِ موردی | آزمون جهت رسانه، Direct Media و سقف منابع |
| ۵. پایلوت | نسخه مشخص، بازگشت‌پذیری و اندازه‌گیری ۵۰/۱۰۰ تماس | عدم افت معنادار کیفیت و تأیید سناریوهای دو مشکل شرکت |

Product Design و UI UX Pro Max در طراحی جریان و خوانایی استفاده خواهند شد و Figma/Storybook پایه‌های موجود را حفظ می‌کنند. ابزار CUA فعلاً خطای راه‌اندازی دارد؛ audit بصری زندهٔ Diagnostics یا طرح نهایی تصویب‌شده ادعا نمی‌شود. بعد از تأیید این گزارش، ابتدا طرح و داده‌های نمونه برای بازبینی آماده خواهد شد.

**تصمیم پیشنهادی برای تأیید:** ابتدا مراحل ۰ تا ۲، با منابع موجود و بدون debug/capture جدید روی PBX؛ سپس تصویب UI و فعال‌سازی اختیاری جمع‌آوری رسانه. توسعه، نصب، تغییر منبع CEL/Dialplan یا فعال‌سازی capture تا تأیید کاربر شروع نمی‌شود.

## تکمیل بررسی پس از تأیید آغاز توسعه

خواندن مستقیم heartbeat در مرحلهٔ پیاده‌سازی، CEL و queue_log تازه را در پیش‌نمایش نشان داد؛ CDR به دلیل نبود پوشش کامل پرچم‌ها unknown بود. بنابراین inactive بودن سرویس با نام استاندارد و قدیمی‌بودن آخرین تماس، به‌تنهایی توقف هر مسیر ingest را ثابت نمی‌کرد. شرح قرارداد و محدودیت جاری در [Diagnostics phase1](DIAGNOSTICS_PHASE1.fa.md) ثبت است.
