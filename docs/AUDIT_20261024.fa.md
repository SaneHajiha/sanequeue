# ممیزی سخت‌گیرانهٔ SaneQueue — ۲۴ اکتبر ۲۰۲۶

این گزارش ارزیابی مهندسی است، نه تضمین «بدون هیچ باگ» یا گواهی Production. معیار امتیاز، صحت داده، امنیت، پایداری، آزمون واقعی و کامل‌بودن قابلیت‌هاست. موفقیت تست‌های یک ماژول به معنی تکمیل کل محصول نیست.

## شاهد آزمون زنده

مجموعهٔ نهایی روی Windows/Python 3.11: **۲۴۷ موفق، ۲ آزمون Redis ردشده از اجرا به علت نبود Redis محلی، ۶۶ subtest موفق، صفر شکست و صفر هشدار** در ۱۵٫۱۱ ثانیه. همان مجموعه روی Rocky Linux/Python 3.11 با Redis واقعی: **۲۴۹ موفق، ۶۶ subtest موفق، صفر شکست و صفر skip** در ۹٫۷۷ ثانیه. پیش از افزودن آخرین تست آزادسازی سوکت، پنج اجرای کامل متوالی Windows بدون گیرکردن موفق شدند. بررسی نحوی دو فایل اصلی JavaScript نیز موفق است.

روی PBX آزمایشی Asterisk 20.12.0 با دو صف عملیاتی و صف مجازی default، Redis 5.0.3 به صورت موقت و فقط روی loopback اجرا شد. این شمارش سه صف خام Collector است؛ نمایش default در رابط تابع تنظیمات نمایش است.

- دو Collector رقابت کردند؛ فقط یکی در ابتدا اتصال AMI داشت.
- ۱۰۰ خواندن هم‌زمان Redis در آزمون نهایی در ۰٫۱۰۶ ثانیه تمام شد؛ تعداد snapshot ناشی از این خواندن‌ها صفر بود.
- فقط سوکت همان Collector قطع شد؛ reconnect و resync با generation تازه موفق بود.
- پس از توقف Collector فعال، standby مسئولیت را گرفت.
- پس از توقف هر دو، state به‌صورت stale خوانده شد و هیچ سوکت Collector باقی نماند.
- هیچ reload/restart روی Asterisk، تغییر مسیر تماس یا فرمان کنترلی برای این آزمون لازم نشد.

این آزمایش کوچک و کوتاه روی سرور بدون بار است؛ ظرفیت هزار تماس یا صدها داشبورد را اثبات نمی‌کند. هنوز soak test چندروزه، packet loss، Redis outage طولانی و اندازه‌گیری CPU/RSS در بار واقعی انجام نشده است.

## موارد باز؛ نباید سبز یا «کامل» نمایش داده شوند

۱. API و رابط فعلی هنوز snapshot cache و listener قبلی دارند. وجود Collector جدید به‌تنهایی ضدالگوی کل محصول را رفع نمی‌کند. باید همهٔ مسیرهای خواندن عادی، از جمله channel probe و اتصال هنگام import، مهاجرت کنند.

۲. AMI snapshot اتمیک نیست و CoreShowChannels به‌تنهایی Bridge graph یا صف تماس پاسخ‌داده‌شده را بعد از reconnect بازسازی نمی‌کند. دادهٔ نامنتسب نباید به کاربر scoped تحویل داده شود. مقادیر `history_complete` و `initial_call_scope_complete` فعلاً false هستند.

۳. `Holdtime` و `TalkTime` در QueueParams خلاصهٔ PBX هستند؛ از آن‌ها نباید AHT/ASA دلخواه یا hold بعد از پاسخ ساخته شود. SLA بدون مشخص‌کردن reset/window و مخرج، مقایسه‌پذیر نیست.

۴. در گزارش‌گیر فعلی `qpanel/reporting.py` شناسهٔ تماس از مدل رویداد حذف می‌شود. cursor فایل به تنهایی dedup قابل‌اتکا پس از rotation/reimport نیست. گزارش تاریخی و CDR در این فاز بازنویسی نشده‌اند؛ گزارش‌گیری فاز بعد باقی می‌ماند.

۵. کنترل ظرفیت فعلی قفل درون پردازش دارد. قفل و رزرو durable بین چند worker و reconciliation لازم است. سیاست برنامه نمی‌تواند جلوی تغییر مستقیم صف از تلفن یا CLI را بدون مکانیزم PBX بگیرد.

۶. دریافت صدا از داخلی ۱۰۰ در شنود/نجوا/ورود با تلفن ۳۰۰ توسط کاربر تأیید شد. چون ۲۰۰ و ۳۰۰ میکروفون نداشتند، مسیر برگشت صدا و جداسازی نجوا آزمون کامل نشده است. AMI accepted به معنی صحت صوت نیست.

۷. Issabel 4/5 و Asterisk 16/18 فعلاً صرفاً پوشش fixture/سازگاری نحوی دارند؛ فقط Asterisk 20.12 روی میزبان فعلی آزموده شده است. بدون VM و آزمون واقعی، برچسب تأیید سازگاری همهٔ نسخه‌ها داده نمی‌شود.

۸. SSO بومی Issabel، WebSocket احراز هویت‌شده، outbox پایدار اعلان، گزارش‌گیری کامل و ضمانت‌های چندگرهی هنوز تکمیل نیستند. منوی موجود جای شاهد پیاده‌سازی را نمی‌گیرد.

۹. برند قابل‌مشاهده SaneQueue است. مسیر asset جدید `/assets/` اضافه شد؛ کد مشتق‌شدهٔ قدیمی هنوز namespace داخلی دارد و طی مهاجرت جایگزین می‌شود. LICENSE/NOTICE و انتساب قانونی عمداً باقی می‌مانند؛ پاک‌کردن آن‌ها تغییر برند محسوب نمی‌شود.
