# Diagnostics — هستهٔ اولیهٔ مراحل ۰ تا ۲

تاریخ: ۲۰۲۶/۱۰/۲۸. مبنا: تأیید کاربر پس از [گزارش ارزیابی](ADVANCED_CALL_DIAGNOSTICS_ASSESSMENT.fa.md).

این مرحله API، ذخیره‌ساز و پردازش محدود آرشیو را می‌سازد؛ صفحهٔ اختصاصی Diagnostics، SIP capture، تشخیص قطعی علت یا صدای یک‌طرفه و تأیید نصب زیر بار هنوز آماده نیستند. هیچ debug، سرویس تشخیصی یا تغییر Dialplan خودکار فعال نمی‌شود.

## قابلیت‌های ساخته‌شده

- `diagnostics/health.py`: خواندن heartbeatهای ثبت‌شدهٔ importer با query کوتاه محلی. حالت‌های unavailable/unknown/stale/error/catching_up/current/snapshot جدا هستند. قدیمی‌بودن آخرین تماس، به‌تنهایی خرابی نیست. snapshot هم پوشش زنده محسوب نمی‌شود.
- `diagnostics/store.py`: SQLite خصوصی/WAL جدا (بودجهٔ schema اولیه ۵ ثانیه، نوشتن عادی ۱ و خواندن پیش‌فرض ۰٫۵ ثانیه)، محدودهٔ همهٔ صف‌های مرتبط، reporter-own، شواهد و اقدامات immutable، optimistic version، صفحه‌بندی keyset، checkpoint اتمیک و بدون حذف خودکار تاریخچه. نام صف Unicode تا ۱۲۸ نویسه بدون تغییر هویت پذیرفته می‌شود.
- `diagnostics/rules.py`: نامزد قطعهٔ کوتاه و کامل صف پس از پاسخ؛ coverage/outcome/duration باید معتبر باشند. مدت قطعهٔ صف با کل مکالمه یکی نیست. انتقال یا مدت مجهول، خودکار خرابی محسوب نمی‌شود.
- `diagnostics/worker.py`: فقط آرشیو گزارش را می‌خواند؛ شماره، channel، SIP payload یا صوت را کپی نمی‌کند. یافته‌ها همیشه suspected/needs_review و دارای نسخه/سیاست و مرجع شاهد هستند.
- `api/diagnostics.py`: ثبت گزارش دستی وابسته به مراجعهٔ مجاز صف، مشاهده و گردش کار مورد، و سلامت منابع برای مدیر دارای دسترسی کامل. این API همراه install گزارش‌ها ثبت می‌شود؛ UI آن هنوز اجرا نشده است.

## بررسی تازهٔ منبع واقعی

بررسی خواندنی بعدی روی همان آرشیو پیش‌نمایش نشان داد heartbeat مربوط به CEL و queue_log تازه و caught-up است؛ CDR به دلیل نبود همهٔ پرچم‌های لازم در آخرین heartbeat، unknown بود. هیچ فعال‌سازی یا تغییر سرویسی برای این مشاهده انجام نشد.

این مشاهده، برداشت صرفاً مبتنی بر inactive بودن نام سرویس `sanequeue-reporting` یا قدیمی‌بودن آخرین تماس را محدود می‌کند: جمع‌آوری می‌تواند از runner دیگری انجام شود و ترافیک ساکت نیز رویداد تازه تولید نمی‌کند. نتیجهٔ زندهٔ این تست، جای تضمین دوام ingest، تنظیم درست منبع یا دریافت رسانه را نمی‌گیرد. API سلامت جدید نام فرایند یا systemctl را در هر درخواست اجرا نمی‌کند.

## قرارداد API فعلی

| مسیر | رفتار |
|---|---|
| GET `/api/diagnostics/source-health` | فقط admin با منوی گزارش و دسترسی تمام صف‌های شناخته‌شده؛ صرفاً heartbeat آرشیو |
| GET/POST `/api/diagnostics/incidents` | لیست خصوصی یا ثبت دستی برای visit مجاز |
| GET/POST `/api/diagnostics/incidents/<id>` | جزئیات خصوصی یا اقدام versioned |

ثبت دستی JSON با کلیدهای `kind`, `visit_id`, `occurred_at` اختیاری و `description` اختیاری است. kind فقط one_way_audio، unexpected_disconnect یا media_quality است؛ این **گزارش کاربر** است، نه اثبات فنی مشکل. queue/role/reporter از payload پذیرفته نمی‌شوند. شناسهٔ مراجعه باید از گزارش مجاز آمده باشد؛ شماره‌گیری یا انتخاب شناسهٔ تماس دلخواه از این API ممکن نیست.

POST به نشست معتبر و `X-CSRF-Token` نیاز دارد. بدنه حداکثر ۸KiB، شرح ۱۰۰۰ و یادداشت اقدام ۲۰۰۰ نویسه است. account در دیتابیس با شناسهٔ HMAC دامنه‌دار ذخیره می‌شود؛ تعویض secret نشست نیازمند طرح مهاجرت برای reporter-own است.

اقدام‌ها: acknowledge، resolve، reopen و comment؛ برای تغییر وضعیت expected_version مثبت اجباری است و comment می‌تواند بدون آن ثبت شود؛ کارشناس فقط روی گزارش خودش comment می‌گذارد. مدیریت پرونده، علت فنی را confirmed نمی‌کند. resolve پایان گردش کار است؛ root_cause و human_intent در این نسخه unavailable باقی می‌مانند.

scope فعلی، مجوز موجود reports/view را استفاده می‌کند؛ مجوزهای مستقل capture/confirm-root-cause هنوز اضافه نشده‌اند و endpoint متناظر ندارند. محدودیت تازهٔ agent/assignment cutoff و تمام صف‌های فعلی همان UID دوباره بررسی می‌شوند. اگر projection عقب باشد، API شواهد ناقص را مجوز تلقی نمی‌کند. توضیح یا یادداشت دیگران بدون مجوز نمایش شماره، نمایش داده نمی‌شود؛ متن خود گزارش‌کننده قابل مشاهده است. متن خصوصی ممکن است اطلاعات شخصی داشته باشد و در log نوشته نمی‌شود.

صفحه‌بندی حداکثر ۱۰۰ ردیف است. from/to همان تاریخ میلادی و timezone تهران گزارش‌ها را استفاده می‌کند، اما فیلتر incident بر **زمان ثبت گزارش** است، نه زمان ورود تماس. مجوز مراجعه مستقل از این بازه بررسی می‌شود. خروجی فعلاً تعداد کل/aggregate جهانی ندارد. cursor نباید شناسهٔ موردی را که در بازبینی مجوز پنهان شده منتشر کند. ردیف‌های با مالکیت تغییریافته تا سقف ۲۰۰ مورد در حداکثر چهار خواندن بررسی می‌شوند؛ رسیدن به سقف با scan_limited=true مشخص است و به معنی تمام‌شدن داده نیست. اگر بازبینی نهایی دسترسی، candidate را حذف کند، refresh_required=true و پاسخ جزئی اعلام می‌شود؛ cursor پنهان منتشر نمی‌شود.

## اجرای اختیاری worker

هیچ service/timer خودکاری نصب یا روشن نشده است. فقط پس از انتخاب آرشیو، دیتابیس مستقل و generation ثابت، یک batch اجرا می‌شود:

```bash
python -m sanequeue.diagnostics.worker \
  --archive /path/to/history.sqlite3 \
  --database /path/to/diagnostics.sqlite3 \
  --archive-generation "$DIAG_ARCHIVE_GENERATION" \
  --disabled-file /path/to/module.disabled \
  --limit 250 --once
```

generation باید `archive_` به‌اضافهٔ ۳۲ رقم hex کوچک باشد، یک‌بار برای همان آرشیو ساخته و ثابت نگهداری شود. آن را در هر اجرا دوباره نسازید و برای آرشیو نامرتبط استفاده نکنید. path/inode/PBX، anchor رخداد و نسخهٔ projection به checkpoint مقیدند. reset/restore/تعویض نسخه، خودکار با cursor قبلی تفسیر نمی‌شود؛ مهاجرت کنترل‌شدهٔ آن هنوز گام بهره‌برداری جداست و حذف دیتابیس قبلی راه‌حل پیشنهادی نیست.

هر batch حداکثر ۱۰۰۰ رخداد و ۱۰۰ مشاهده دارد؛ SQL reader و حلقه deadline دارند. ابتدا باید projection به head همان snapshot رسیده باشد. این سقف، تضمین مصرف CPU یا ظرفیت ۱۰۰ تماس نیست. غیرفعال‌سازی پیش از شروع و پیش از commit کنترل می‌شود. تغییر سیاست آستانه، شناسهٔ قاعدهٔ جدا دارد؛ مقدار آستانه نیز immutable ذخیره می‌شود تا نتیجه پس از restart قابل بازخوانی باشد.

API تطبیق ساده با visit فعلی را فقط با سیاست ذخیره‌شده بررسی می‌کند. حتی وقتی این تطبیق برقرار باشد، `current_state_verified=False` است: بازسازی کامل همهٔ اصلاحات دیررس CEL و شبکه هنوز وجود ندارد. دادهٔ تاریخی با علت قطعی فعلی یکی نیست.

## اصلاحات مرتبط گزارش‌گیری و مرز ارتقا

۱. `userdeftype` ستون اختیاری importer CEL شد. نبود ستون با NULL سازگار است؛ anchor قدیمی به نسخهٔ ۲ مهاجرت می‌کند تا افزودن این فیلد reset کاذب نسازد. دادهٔ قبل از cursor خودکار backfill نمی‌شود.

۲. LOCAL_OPTIMIZE_END فقط با نام Local صریح و معتبر edge می‌سازد؛ از آن مالکیت یا قطع‌کننده حدس زده نمی‌شود. ENDهای تاریخی قدیمی هنوز backfill کامل ندارند.

۳. اصلاح مستقلِ source-version گزارش صف: نسخهٔ اصلاح‌شدهٔ COMPLETE دیگر visit اضافی تولید نمی‌کند. آخرین نسخهٔ منبع تا watermark همان batch انتخاب می‌شود؛ identity قدیم و جدید بازسازی می‌شوند. raw history و snapshot خروجی قدیمی حفظ می‌شوند. guard ده‌هزار شاهد خام و استفادهٔ ایندکس آزموده شده‌اند.

projection به **۱۰** می‌رود و replay محدود از ابتدا انجام می‌شود. در این بازه، گزارش مشتق‌شده می‌تواند موقتاً جزئی باشد؛ Diagnostics تا catch-up منتظر می‌ماند. binding تشخیصی روی projection قبلی باید برای مهاجرت بازبینی شود. این تغییر روی PBX نصب نشده و نباید بدون backup و برنامهٔ ارتقا روی محیط زیر بار اعمال شود.

## مواردی که این مرحله تکمیل نمی‌کند

- تشخیص فنی صدای یک‌طرفه، تاریخچهٔ RX/TX، کدک/SDP، BYE/CANCEL و SIP dialog mapping.
- Call Journey عمومی همهٔ تماس‌های داخلی خارج از صف، قطع‌کنندهٔ قطعی تماس پیچیده یا قصد انسان.
- داشبورد و گزارش تصویری اختصاصی، اعلان خودکار incident و مستقل‌سازی همهٔ مجوزهای Diagnostics.
- فعال‌سازی عمومی importer، backfill تاریخی، مهاجرت خودکار binding پس از restore و تضمین سربار.
- آزمون تلفنی جدید، Direct Media، نسخه‌های دیگر PBX و ۵۰/۱۰۰ تماس واقعی.

این محدودیت‌ها در فهرست قابلیت‌ها نیز ثبت می‌شوند. گام بعد، پذیرش هسته و سپس طراحی صفحه با Product Design/UI UX Pro Max/Figma و fixtureهای فاقد اطلاعات مشتری است؛ پیاده‌سازی بصری گسترده مطابق workflow بعد از تصویب طرح انجام می‌شود.
